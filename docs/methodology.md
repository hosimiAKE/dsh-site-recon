# 这套方法是从哪次实践里长出来的

> 一份方法论如果只讲"应该怎样"，它说服不了任何人。这里记录的是：一次真实的官网调研里，**具体哪一次翻车**逼出了哪一条规则，以及那条规则最后被写进了哪个工具。

原始任务：调研 Salesforce 官网，弄清它如何把 AI 深度整合进实际业务，并把结论落到提问者自己的系统架构上。要求里最硬的三条是——

1. 要**礼貌**，像人一样一个页面一个页面地看，"读懂一个，再查看一个"；
2. 每一个论点都要有**链接与截图**作佐证；
3. 最后要**务实、可操作**，能对上真实的架构决策。

---

## 一、第一次翻车：一张裁错的图

报告写完后，提问者的第一句反馈是：

> 图片「五个系统的堆叠」截取错了。

原因是自动切片：整页长图按 1250px 切段，而那张五层堆叠图**恰好横跨两段切片的边界**——上半截在上一张，下半截在下一张。被引用的那张只剩三行，最上面一行还被切掉一半，底下两层完全不见了。

这里暴露的不是手滑，而是一个更普遍的错误：**图注描述的是"那张图应该是什么"，而不是"那张图实际显示了什么"。** 图注说"五层堆叠完整可见"，画面里只有三层半。

> **法则一：断言不得大于证据。**
> 图注不能比画面说得更多，结论不能比引文说得更多。证据只支持 70%，就只写 70%，剩下 30% 放进"尚未回答"。
>
> **落点：** `recon_evidence` 拒收快照里找不到的引文；`recon_audit` 检查每条断言的证据状态；报告里"无证据"的断言被强制移出"发现"。

## 二、第二次翻车：靠猜来对齐

修正那张图时，模型的做法是"再截一次试试"，靠肉眼判断有没有截对。提问者随即给了整个任务里最关键的一句话：

> 你可能需要首先编写一个更加可靠的 agent 来帮助你截图，至少要做到**手脑协同**吧？而不是在这里瞎猜。

这句话改变了工作方式。接下来做出来的截图 agent，流程是固定的六步：

1. **先量**：在页面里找到目标元素，读出它的绝对坐标与尺寸；
2. **再动**：滚动到能容纳它的位置；
3. **复测**：重新量一次，偏差超过 14px 就再修一次；
4. **查遮挡**：在目标区域三个点取样，看最上层是不是浮窗；
5. **落盘后校验**：统计像素（空白率、暗色率、右边缘白边、MD5），空白帧直接判废；
6. **失败重试**：换锚点、换等待、换目标文本，而不是把同一动作重复三遍。

每一张被引用的截图都附带一份 JSON 记录：目标文本、`rect`、是否在视口内、遮挡命中、像素统计。截图不再是"我觉得可以"，而是"量过两次、查过遮挡、像素统计达标"。

> **法则二：先测量，再动作，再复测，最后才相信。**
> 你要描述的东西，先量它；动完再量一次；量到一致才落笔。猜出来的位置，写进报告就是错的。
>
> **落点：** `recon_capture` 的六步流程；`recon_fetch` 对"被拦截 / 客户端渲染 / 正文过薄"的显式判定；`recon_audit` 要求每条证据有 `locator`。

## 三、第三次教训：证据要能被别人复核

第二次修完，提问者没有再验收图片，而是要求：

> 请你确认所有的截图都是正确的，并为文章中的每一个出现的 Evidence，添加可以点击跳转的链接。

注意要求的方向：不是"再解释一遍为什么对"，而是**让读者自己能去核对**。于是 60 处 `【E01】…【E16】` 全部变成可点击链接，附录 A 每一条都写明 URL 与"它证明了什么"。

这把证据从"作者的自证"改成了"读者的可验证"。

> **法则三：证据的存在形式必须让第三方能复核。**
> 一句结论配一个可点击的原文位置，比配一段自信的解释有用得多。
>
> **落点：** 证据编号 `E##` + `locator` + 快照文件；报告附录 A 直接给原文引用与 URL；`【E##】` 作为正文引用约定。

## 四、那次调研撞到的具体墙

这些是环境层面的、会反复出现的坑。它们后来都变成了框架里的检测与对策：

| 现象 | 真正的原因 | 对策（已入工具） |
|---|---|---|
| 无头浏览器直接 403 | CDN 拦截自动化特征 | 覆盖真实 UA、关闭自动化标志；仍失败就换来源 |
| 整页截图为空白 | 固定高度 iframe + 懒加载 | 先滚到底触发加载，再逐屏截，不要整页截 |
| 文档站滚不动 | 内部滚动容器，不是文档流 | 按元素坐标定位，而不是按页面滚动（`recon_capture`） |
| 正文被浮窗盖住 | 浮动 AI 助手在自定义元素的 shadow DOM 里 | 定点隐藏该子树，不能整块隐藏宿主（会连首屏一起隐藏） |
| 同一页两次标题不同 | 首屏文案 A/B 轮换 | 以稳定段落/章节标题为锚点，不要锚 H1 |
| 搜索结果看起来什么都有 | 摘要不是正文 | 登记≠覆盖；没读进来不算证据 |

> **法则四：把环境故障当成信息，而不是噪声。**
> "这页读不到"本身就是一条结论，写进报告比硬编一个来源诚实。
>
> **落点：** 来源状态区分 `seen` / `fetched` / `blocked`；`recon_fetch` 明确说"这是墙，不是页面，别引用它"。

## 五、还有一条，是关于"顺着走"

原始要求里那句"不是一次拉取很多页面，而是顺着思路，浏览并分析，读懂一个，再查看一个"，当时看起来只是礼貌要求，事后看是**结构性**的：

- 顺着页面自己出现的链接走，报告的结构天然就是这个领域的信息结构；
- 每读一页就归纳一次，后一页的问题由前一页的答案长出，而不是由预设提纲长出；
- 单页顺序访问也让"这条结论是哪一页读出来的"永远可回答。

预先爬 50 个 URL 再统一分析，会同时丢掉这三样东西。

> **法则五：路径本身是方法的一部分。**
> 同样的材料，按证据链走出来的结论，和按提纲填出来的结论，可信度不一样。
>
> **落点：** `recon_map` 只顺着入口页自己的链接走且带页数预算；`recon_fetch` 按 host 限速一次一页；`recon_gaps` 建议的下一步永远指向"空着的那类来源"，而不是"再多搜几个词"。

## 六、从一次调研抽象成一个框架

把上面五条翻译成机器能检查的状态，就是这套插件：

| 原来的做法 | 抽象后 | 谁在强制执行 |
|---|---|---|
| 人工记得"要交叉验证" | 11 类来源角色 + 覆盖矩阵 | `recon_gaps`、`recon_audit` |
| 人工记得"这里还没想透" | 8 级深度阶梯，按级计分 | `recon_probe` |
| 人工核对引文有没有抄错 | 快照 + 逐字匹配 | `recon_evidence` |
| 人工记得"图注别写过头" | 断言状态由证据推导，无证据不进发现 | `recon_report` |
| 人工记得"这张图截对没有" | 测量→复测→遮挡→像素四道校验 | `recon_capture` |

一句话总结这次实践给出的方法论：

> **好的调研不是"我知道得多"，而是"我说的每一句，你都能自己查到"。**

框架剩下的部分，都是为了让这句话在没人盯着的时候也成立。
